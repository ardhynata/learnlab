# Claude Code instructions for learnlab

Project-level behavior guidance for Claude Code sessions in this repository.

## Review gate

Every PR gets a blocking review sized by risk tier, and a `REVIEW: PASS` at the PR's current head sha is what lets the orchestrator merge. Design note: [`docs/design/review-gate.md`](docs/design/review-gate.md). The gate is installed by the Hexago review-gate kit (the Go gate, `hexago review-gate guard`); `.hexago-review-kit.json` records which kit version this repository carries.

- **Flow.** The agent finishes and its local gates pass (build, vet, lint, tests, doc gates); the branch is current with the trunk (`git merge`, never a force-push); the PR is opened or kept as a DRAFT (`gh pr create --draft`); the review is requested on that exact commit at the tier's reviewer (the `pr-reviewer` agent, `.claude/agents/pr-reviewer.md`); ONE fix commit applies every blocking finding AND every improvement; the reviewer re-checks only that commit; on PASS the orchestrator runs `gh pr ready`, watches CI to green by check name and merges. A commit after the PASS makes it stale and needs a delta re-check.
- **Tiers.** The path-to-tier table is `scripts/review_tiers.json`; `hexago review-gate tier` computes the tier. T0 needs no review; T1 sonnet/high; T2 opus/high; T3 opus/xhigh plus a verify pass (Opus is the top reviewer tier). The highest changed path wins; more than 40 files, more than 1500 changed lines and 2 or more CI fix loops each raise the tier by one, capped at T3. Compute the tier as the hook does: `hexago review-gate tier --root <absolute path of this checkout> --paths - --lines <additions+deletions>` over the PR's REST file list (`gh api repos/<owner>/<repo>/pulls/<N>/files --paginate`), feeding BOTH `filename` and `previous_filename` of every entry (`--root` must be absolute: the table is read from `<root>/scripts/review_tiers.json`, never from the working directory). A path no rule matches exits 2 as UNCLASSIFIED and blocks until the table is updated.
- **Owner-only tier.** A rule in `scripts/review_tiers.json` may name the tier `owner` (for example `{"glob": "gen/rate.yaml", "tier": "owner", "reason": "rates change money"}`; `reason` is optional free text the denial shows). `owner` ranks above T3 and no marker can name it (the marker grammar stops at `T3`), so the hook ALWAYS denies a PR that touches such a path, whatever the review says, and the owner merges it by typing the merge command themselves (the denial names the ways: a terminal, the GitHub button, or the `!` prefix of the Claude Code prompt). A reviewer's PASS on it is advice for the owner and unlocks nothing; review it at T3 rigor and post `tier=T3`. A bump never reaches `owner` and `--min-tier` does not accept it: only a rule can. Add an `owner` rule only after every machine that merges has moved to the Go hook: the Python classifier of kit v1 to v3 (`scripts/review_tier.py`) crashes with a traceback (exit 1) on a PR that touches an owner path, and the Python hook then denies that merge as a classifier error.
- **Review-system files (selfgov).** `scripts/*.py` (every Python file directly under scripts, not nested ones), `scripts/review_tiers.json`, `scripts/review-gate.pin`, `.hexago-review-kit.json`, `.claude/agents/pr-reviewer.md`, `.claude/agents/pr-shipper.md`, `CLAUDE.md` and `docs/design/review-gate.md` need TWO independent opus PASSes (`pass=1` and `pass=2`). The merge hook holds more than the first list to two passes: it applies Hexago's whole gate list, which also names Hexago's own gate sources and kit emitters, `scripts/review_tier_test.go`, `scripts/review_gate_guard_test.go`, `scripts/rg_*.go`, `scripts/parity/**`, `internal/reviewgate/**`, `internal/hooks/**`, `internal/commands/review_gate*.go`, `internal/commands/hook*.go`, `internal/commands/root.go`, `internal/commands/scaffold_review_gate*.go`, `cmd/hexago/**`, `internal/doctor/rules_review_gate*.go`, `internal/upgrade/rule_review_gate_kit*.go`, `internal/generator/templates/reviewkit/**`, `internal/generator/review_kit_parity_test.go` and `internal/generator/review_kit*.go`. A product path that matches one of these (`internal/hooks/**`, `internal/commands/root.go` and `cmd/hexago/**` can exist in a product) needs two passes too. `hexago review-gate tier --root <absolute path of this checkout>` is the authority for the tier and flags `selfgov` for most of both lists, but NOT for the pin, the kit stamp or the paths of the second list that start with scripts/rg_, scripts/parity, internal/reviewgate, internal/hooks, internal/commands, cmd/hexago, internal/doctor or internal/upgrade, so apply those by hand.
- **Marker.** A PR comment from the owner account only (comment `user.type` is `User` and the login is the authenticated one). Its first line is exactly `REVIEW: PASS|BLOCK tier=Tn model=<sonnet|opus|fable> [fallback=fable-limit] sha=<40 lowercase hex> [pass=1|2]`: `model` is the lowercase family word, not a full model id (new reviews post `opus` or `sonnet` by default; `fable` is posted only for an owner-requested Fable review, and older `fable` markers stay valid); the optional `fallback=fable-limit` token is DEPRECATED and meaningless but still parses exactly there, at most once and with no other spelling; the full 40-character head sha; no BOM, no leading space or blank line, no trailing space; only the first line is read. A comment by a bot or any other author is ignored. A findings table follows (severity blocking|improvement, file:line, claim, evidence, disposition). A PASS counts when no BLOCK for that head sha comes after it; for selfgov a BLOCK by either pass invalidates the other pass's earlier PASS.
- **Opus is the top reviewer tier.** T3 and selfgov are reviewed by Opus (opus/xhigh) and the hook accepts `model=opus` there with no extra token. Selfgov needs TWO independent `model=opus` PASSes (`pass=1`, `pass=2`), and the hook raises the required tier to T3 for a selfgov PR at every path tier (not only T0), so each pass must carry `tier=T3`. `model=sonnet` never satisfies T3 or selfgov. A `model=fable` marker already posted stays valid because the hook ranks fable above opus, but a new review is spawned on Fable only when the owner asks for one (the next two bullets). The older Fable-limit fallback is retired: the `fallback=fable-limit` token still parses so old markers stay readable, but it carries no meaning, never changes what a marker is credited as, and a BLOCK carrying it still invalidates earlier PASSes of the same head like any BLOCK. The `model=` field is self-declared, a tripwire and not proof of which model ran.
- **Fable on request.** The owner may ask in chat for a Fable review of any PR. The orchestrator then spawns `pr-reviewer` with model fable and effort xhigh, and the marker says `model=fable`. The hook accepts it at every tier (fable ranks above opus), and on a selfgov PR a `pass=1` and a `pass=2` both posted as `model=fable` count, as does a mix with an opus pass. On a Fable usage-limit error the orchestrator asks the owner (wait, or use Opus) and never relabels an Opus review as `model=fable`.
- **Timed Fable question.** The orchestrator may RECOMMEND a Fable review for a specific PR (for example one that changes hook marker parsing or the trust check), but only the owner's approval makes it happen. It asks the owner in chat with the reason, a rough cost and a default deadline of 5 minutes, then keeps working on other units. An explicit yes in chat spawns the Fable review; a no, or silence past the deadline, means Opus continues: silence is never approval for Fable. If a Fable usage-limit error follows a yes, the orchestrator tells the owner and uses Opus only if the owner says so. The wakeup that marks the deadline fires only while the session is alive; otherwise the question waits for the next session.
- **T3 model cross-check.** The marker's `model=` is self-reported, and the hook cannot see which model actually ran. Before merging on a T3 marker (and on each selfgov pass) the orchestrator checks the marker against the reviewer agent's journal model (the `"model"` field of `~/.claude/projects/<project>/<session>/subagents/agent-*.jsonl`); for a T3 marker that model must be Opus (or Fable, for a marker posted before 2026-11-06 or for a review the owner asked for in chat).
- **Merge command.** `gh pr merge <literal N> --squash --delete-branch --match-head-commit <40-hex head sha>`. The hook enforces a literal PR number, the `--match-head-commit <head sha>` pin and no `--auto` or `--admin`.
- **Hook.** `hexago review-gate guard --root "$CLAUDE_PROJECT_DIR"` (PreToolUse, `Bash`) refuses `gh pr merge` without a valid PASS for the PR's head sha and denies pushes to the repository's default branch. Its trust check compares the tier table (`scripts/review_tiers.json`) and the pin (`scripts/review-gate.pin`) with the PR's base branch on the local remote whose URL names the PR's repository, so fetch it first (`git fetch <remote> <base>`), and requires that the gate digest of the running hexago binary equals the pin (`hexago review-gate pin-check --root <absolute path>` runs that comparison alone). While the project still carries the kit v1 to v3 scripts (`scripts/review_tier.py`, `scripts/review_gate_guard.py`, `scripts/gate_pipe_guard.py`) they must equal the base branch's too. The pin is a tripwire against a stale or wrong-version gate, not proof of what a process runs, and the hook as a whole is a tripwire against forgetting, not a security boundary: it cannot catch what the command text hides (an alias, a script written in an earlier call, a renamed `gh`), and `.claude/settings.json` is gitignored so unwiring it needs no PR.
- **Wiring (per machine, AFTER the pin and the table are on the trunk).** The hook is a `Bash` PreToolUse entry in the gitignored `.claude/settings.json`: `<absolute path of a hexago binary> review-gate guard --root "$CLAUDE_PROJECT_DIR"` with `"timeout": 10` and `"onFailure": "block"`. The binary must be one whose gate digest equals the pin on the trunk (`hexago review-gate pin` prints the digest; `hexago review-gate guard --selftest` must exit 0), because a hook that names any other binary denies every merge. `hexago scaffold review-gate` says whether it wired the hook and, when it did not, why; wire the entry above by hand when it did not. `hexago init` never wires the hook, and `--no-wire` makes the scaffold verb skip the wiring step. A missing binary under `onFailure: block` blocks every Bash call: if that happens, remove the entry with the Edit tool or from a terminal outside the session. Merge the pin and the table first, wire second.
- **Moving the pin.** Every change to the Go gate sources changes the digest, so a hexago built from newer sources no longer equals the pin and denies every merge until the pin moves. The pin moves in a reviewed PR (selfgov, two passes): run `hexago upgrade --only review-gate-kit` with the newer hexago, and merge it from a checkout on the trunk. Keep the hook on the binary whose digest equals the CURRENT trunk pin until that PR has merged: the PR is judged by the old gate, and a hook already moved to the newer binary denies its merge. Then fast-forward and wire the newer binary. `hexago review-gate pin-check --root <absolute path of this checkout>` says whether the checkout's pin is the running binary's.
- **Bootstrap.** The PR that introduces the gate cannot be reviewed by it: the trust check fails closed until the pin and the table are on the trunk, so the owner merges that one PR (operator hatch `HEXAGO_ALLOW_UNREVIEWED_MERGE=1`, explicit operator approval only).
- **Not delegated.** The human gate stays for user-authored commits, a PR labelled `needs-review`, a bypassed check and any lowered coverage floor. A PASS never overrides a red or CANCELLED check.
