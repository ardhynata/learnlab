# learnlab

A Go service scaffolded with [Hexago](https://github.com/inxpirativ/hexago) — hexagonal-architecture codegen substrate.

## Stack

| Layer        | Choice                                |
|--------------|---------------------------------------|
| Module       | `example.com/learnlab`                       |
| Transports   | rest           |
| Database     | postgresql |
| Storage      | none |
| Config format| env |
| Migrations   | goose v3 (`db/migrations/`) |

## Quickstart

```bash
make dev
```

`make dev` brings up the docker-compose dependencies (`postgres`), sources `.env.local`, and runs the app against the local stack.

The REST API is at <http://localhost:8080> (default `HTTP_ADDR`); `GET /healthz` returns `ok`.

## Production (`make run-prod`)

1. Populate `.env.production` with real credentials. The file ships with commented templates for Cloudflare R2 / AWS S3 / self-hosted MinIO / Backblaze B2 — uncomment the one matching your deployment and fill in the values.
2. `make run-prod`

`run-prod` doesn't start docker-compose dependencies — production runs against managed services (RDS, Atlas, R2, etc.). The same Go binary runs against any of them; the seam is the env-var set, not the code.

## Stop / restart

```bash
make stop          # kill the app process (works from another terminal)
make compose-down  # tear down docker-compose services (preserves data volumes)
```

## Credentials

| File              | Committed? | What                                       |
|-------------------|-----------|--------------------------------------------|
| `.env.example`    | yes       | Documentation template (empty values)      |
| `.env.local`      | **no**    | Local-dev defaults + freshly-generated keys |
| `.env`            | **no**    | Dev-stack container credentials `docker compose` reads (random per project) |
| `.env.production` | **no**    | Production secrets — cloud-deploy templates |

`.env`, `.env.local` and `.env.production` are in `.gitignore`. The dev database / MinIO passwords in `.env` and the DSNs / S3 keys in `.env.local` were generated together at `hexago init` time and match each other; the dev stack ships no well-known default credentials (rotate by deleting both files, re-initialising and running `docker compose down -v`). **Never commit a populated env file.** The `ENCRYPTION_KEY` / `BLIND_INDEX_KEY` in `.env.local` were generated freshly at `hexago init` time (one shot of `crypto/rand.Read`); replace them in `.env.production` with values from your secrets manager — never reuse dev keys in prod.

## Schema migrations

Schema lifecycle is split between two mechanisms that **coexist**:

- **First boot of a fresh DB** — the generated outbound adapters in `internal/adapter/outbound/<entity>/repository.go` run `CREATE TABLE IF NOT EXISTS` inside their `NewRepository(...)` call. Tables appear with no manual step. **No migrations needed.**
- **Going forward** — every column add, rename, type change, index, or constraint lives in `db/migrations/` as a [goose](https://github.com/pressly/goose) `.sql` file. `make migrate-up` applies them; `make migrate-down` rolls the most recent one back. The auto-init covers fresh-DB scenarios; migrations cover evolved-DB scenarios.

### Hard rule

**Never edit the generated outbound adapters in `internal/adapter/outbound/*/repository.go` to alter columns.** Those files are regenerated by `hexago gen` and any hand-edit is silently overwritten on the next regen. Migrations own column state after first boot — that is the seam between codegen and operational schema.

### Workflow

```bash
# Scaffold a new migration (creates db/migrations/<timestamp>_add_phone_to_customers.sql)
make migrate-create name=add_phone_to_customers

# Edit the generated file. Fill in BOTH the +goose Up and +goose Down
# blocks. Down must restore the previous state — never leave it as
# `-- TODO`, because `make migrate-down` runs it verbatim and a
# missing Down means rollback is silently a no-op.

# Apply (sources .env.local by default).
make migrate-up

# See state.
make migrate-status

# Roll back the most recent migration (irreversible-DDL caveat below).
make migrate-down

# Production: same targets, MIGRATE_ENV=prod sources .env.production.
MIGRATE_ENV=prod make migrate-up
```

### Notes

- The `00001_baseline.sql` file is documentation-only — its Up/Down bodies are `SELECT 1;` no-ops. It exists so `goose status` shows a clean baseline row, and so a reviewer can read the coexistence contract from the migrations directory without spelunking through generated code. The version is `00001` (NOT `00000`) because goose rejects version 0.
- The `migrate-*` targets read `POSTGRES_DSN` from the env file via `grep | sed` rather than sourcing — unquoted DSNs containing `(...)` and `&` break shell sourcing.
- Some DDL is irreversible at the data layer (e.g. dropping a column loses data; widening a `BIGINT` to `BIGINT UNSIGNED` reinterprets values). Down migrations restore *schema*, not data. For destructive changes, take a backup before `make migrate-up` in production.
- The goose CLI is invoked via `go run github.com/pressly/goose/v3/cmd/goose@<pinned-version>`; the matching library version is pinned in `tools.go`. Bump them together when upgrading goose.

## Oracle contract

An AI coding agent (or any automated tool) can determine whether the project is broken by running a single command:

```bash
make test       # exit 0 = all tests pass; non-zero = broken
make test-json  # same, with -json output for machine parsing
```

`make test` runs `go test ./...`. DB-integration legs (PostgreSQL, MySQL, MongoDB) skip automatically when the matching `*_TEST_DSN` / `MONGO_TEST_URI` environment variable is unset, so this command always runs cleanly with no database present. The generated `.github/workflows/ci.yml` starts a postgresql instance and exports that variable, so CI runs this project's adapter tests against a real store; locally, export it (see `.env.local`) to do the same.

`make test-json` emits one JSON object per line (the [`go test -json`](https://pkg.go.dev/cmd/test2json) stream):
- Each line is a `TestEvent` with `Action`, `Package`, `Test`, and optionally `Output`/`Elapsed`.
- `Action: "pass"` / `Action: "fail"` / `Action: "skip"` at the `Test` level → per-test result.
- `Action: "pass"` / `Action: "fail"` at the `Package` level → per-package result.
- Process exit code 0 = all packages passed; non-zero = at least one failure.

The generated `ci.yml` in `.github/workflows/ci.yml` runs `make test` + `make arch-check` on every push to `main` and every PR, so CI matches exactly what you run locally.

## Learnlab: run it

Two binaries: the Hexago-generated API (`cmd/app`, port 8080) and the hand-written frontend server (`cmd/web`, port 3100) that embeds `cmd/web/static/` and proxies `/api/*` to the API.

```bash
make dev   # (or: docker compose up -d postgres)  PostgreSQL on 127.0.0.1:5442
make migrate-up                      # goose ledger (schema is created at boot)
set -a; . ./.env.local; set +a       # POSTGRES_DSN, HTTP_ADDR
go run ./cmd/app &                   # API
go run ./cmd/seed                    # load the course catalog (idempotent)
go run ./cmd/web                     # http://localhost:3100
```

- **Content** is files under `cmd/seed/content/`: `paths/<path>.yaml`, `courses/<course>/course.yaml` (metadata and its modules), and one folder per lesson with `lesson.md` (YAML front matter, then the lesson text) and `quiz.yaml`. Re-run `go run ./cmd/seed` after editing; it updates in place and removes what you deleted. `go test ./cmd/seed` checks the whole tree (structure, lesson template, figures, labs, quiz size).
- **Labs.** A lesson with `kind: simulator` names a lab with `simulator: <key>`; the lab is the single file `cmd/web/static/sims/labs/<key>.js` exporting `mount(root) -> destroy()`. There is no registry to edit.
- **Figures.** `[[figure:name|Caption]]` in a lesson uses the shared bundles (`figures/common.js`, `clustering.js`, `nearest-neighbors.js`); a lesson's own figures live in `figures/lessons/<lesson>.js` and are used as `[[figure:<lesson>/<name>|Caption]]`; helpers are in `figures/kit.js`.
- **Database.** PostgreSQL via the project's compose file (`make dev`), host port 5442. Schema changes for Postgres need a hand-written goose migration (`make migrate-create`), because `hexago gen` writes ALTERs for MySQL only.
- Progress is unauthenticated: a random learner id is kept in the browser's localStorage.

## Building a lab

A lab is one file, `cmd/web/static/sims/labs/<key>.js`, built on the kit in `sims/kit/`. Read `sims/labs/distance-playground.js` first: it is the reference lab.

```js
import { createLab, createPlot, drawLineChart, rng, blobs, clusterColor } from '../kit/index.js';

export function mount(root) {
  const lab = createLab(root, { title: 'Feature space', hint: '...', playback: true, status: true });
  const plot = createPlot(lab.canvas);                      // 0..10 square, themed axes, drawing helpers
  const controls = lab.panel([ /* select, range, number, toggle, button, note */ ], () => draw());
  const stepper = lab.stepper({ init, step, isDone, render });   // Run / Pause / Next / Previous step
  lab.onTheme(draw); lab.onResize(draw);
  return lab.destroy;                                        // called when the learner leaves
}
```

- **Math** goes in `sims/ml/<name>.js` as pure functions with a `*.test.js` beside it (`make test-js`). Existing: distances, scaling, k-NN, least squares and polynomial fits, classification metrics, symmetric eigen-decomposition (PCA), seeded datasets.
- `stepper` expects `step` to return a **new** state (never mutate), which is what makes Previous step free.
- `lab.chartCard(title)` adds a second canvas under the plot for curves; draw it with `drawLineChart`.
- Use theme colors only (`clusterColor(i)`, `plot.g.t.*`), label every control, keep the console clean.
- Preview a lab alone at `#/lab/<key>` (not linked from the catalog).

## Curriculum (from `docs/syllabus.txt`)

The catalog follows `ML_Syllabus.docx`: **Level = path, syllabus module = course**, each course two to four short lessons in two parts (Core ideas, Lab). Level 1 (Beginner) is built first; the course page shows "Module N" from the syllabus. Lessons without a syllabus home (gradient descent, learning rate) are parked in `cmd/seed/parked/` for Level 2. Labs that show "the course dataset" start from `SHARED_SEED` in `sims/datasets.js`; labs can offer a Generated / Real data switch (`sims/kit/data.js`) and a "Predict first" box (`sims/kit/predict.js`).
